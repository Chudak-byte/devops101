Файл /etc/passwd має загальну інформацію про доступи користувачів, яка потрібна деяким сервісним тулзам та самим користувачам для роботи тому він відкрити для читання усім. А файл /etc/shadow має хеші паролів які якщо дізнатись то можна за допомогою брутфорсу підібрати їх. Тому читати їх може тільки користувач root і група shadow.
Алгоритм хешування yescrypt так як початок хешування покривається його тегом ($y$) myuser:$y$j9T$jvK. Взятий з /etc/shadow
Такий обліковий запис потрібен певним сервісам, так як вони обслуговуються тільки з цього користувача з міркувань безпеки, і по дефолту у них заблоковано вхід через ssh.

У масці umask 002 - це маска яка надає повні доступи для власника і однієї групи(в якій можуть бути працівнки одного відділу і можуть разом працювати над цим файлом чи директорією).

setfacl -m (флажок modify) працює виключно з теперішніми об'єктами а setfacl -d -m(default + modify) встановлює правила для усіх майбутніх файлів та директорії.

# Звіт про інциденти: Навмисні збої застосунку

## Інцидент 1: Втрата доступу до файлу коду (app.py)
Симптом: Користувач бачить помилку 502 Bad Gateway від вебсервера через відсутність живих бекенд-воркерів Gunicorn.
Докази: PermissionError: [Errno 13] Permission denied: '/srv/flaskapp/app.py'
Причина: Користувач root змінив власника та права файлу app.py на 640 root:root, позбавивши воркерів Gunicorn (працюють від www-data) прав на читання.
Виправлення: sudo chown www-data:www-data /srv/flaskapp/app.py && sudo chmod 644 /srv/flaskapp/app.py && sudo systemctl restart flaskapp
Профілактика: Дотримання принципу найменших привілеїв та заборона виконання прямих ручних маніпуляцій з правами системних файлів застосунку без налаштованого CI/CD.

## Інцидент 2: Втрата доступу до бази даних (guestbook.db)
Симптом: Користувач бачить помилку 500 Internal Server Error, хоча сам сервіс Gunicorn залишається активним.
Докази: sqlite3.OperationalError: attempt to write a readonly database / sqlite3.OperationalError: unable to open database file
Причина: Користувач встановив права 000 для файлу guestbook.db, через що процес під управлінням www-data втратив будь-які права на читання та запис бази даних SQLite.
Виправлення: sudo chmod 644 /srv/flaskapp/guestbook.db
Профілактика: Використання належних систем контролю цілісності файлів, налаштування коректних ACL та моніторингу доступності сховища даних.

Перша команда rm -rf / видалила б усю кореневу систему
Зміна мала пустий рядок коли баш інтерпретує рядок $TARGET/ він таргет замінює на пусте місце через що баш сприймає це як кореневий каталог.
set -u по стандарту ставлять на початку скрипта він припиняє виконання скрипта коли  зустрічає невизначену зміну чи пусте поле. ${TARGET:?refusing to run with an empty target} це вбудований захист параметрів у баш, якщо зміна не існує або порожня скрипт переривається і виводить повідомлення про помилку.
Тому chmod -R 755 флажок -R рекурсивно застосував цей набір правил для усіх файликів усередині папки.
Папкам потрібен біт виконання, щоб туди взагалі можна було зайти через cd або просканувати вміст. Без x директорія просто неприступна.
Звичайним файлам виконання не потрібне взагалом. Якщо ти робиш тупий chmod -R 755, ти робиш виконуваними всі файли підряд, що є потенційною дірою в безпеці.
Три команди: rm -rf $TARGET/ при пусті зміні TARGET, sudo chown -R user: / змінює власника усіх системних файлів після чого машинка повністю ламається, rm -rf $DIR/* при пустій зміні DIR.
